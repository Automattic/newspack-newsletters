# Newsletter Modernisation — Context

This document captures the *why* behind decisions for the newsletter modernisation work — rationale, alternatives considered, constraints that shape the work.

## How to use this doc

This is the contract for anyone — human or AI agent — working on this project:

1. **Before starting a session** on any branch in this project (the project epic, a milestone integration branch, or a per-ticket branch off either): read this doc in full. It tells you what's been decided and why, and which open questions still bind.
2. **Before opening a PR**: identify the right base branch (see *Branch structure* below — per-ticket PRs target their milestone branch, not the project epic). Decide whether your work introduces a decision, gotcha, learning, or shift in scope. If yes, update the relevant section and append a dated entry to the **Decisions log** in the same PR. If no context change applies, say so explicitly in the PR description (e.g. "No context change.").
3. **Tone:** terse but explanatory. Future readers won't have the conversation that produced each decision — they need the reasoning, not just the conclusion.

## Branch structure

Three tiers:

- **`epic/newsletters-modernisation`** — the project epic. Receives only milestone-integration merges. Ultimately merges to `trunk`.
- **`epic/<milestone>`** — one integration branch per Linear milestone (e.g. `epic/admin-ux-modernisation`, `epic/editor-refactor`, `epic/beehiiv`, `epic/de-risk`, `epic/validate`). Receives per-ticket PRs and is QA'd as a coherent unit before promoting to the project epic. Naming: kebab-case version of the Linear milestone name.
- **`news-<id>-<slug>`** — per-ticket branch cut from its milestone integration branch. PRs target the milestone branch.

**Why three tiers.** Newsletters are critical and the modernisation is wide-ranging. We want each milestone to land on the project epic only after it's been tested as a unit (cross-ticket integration, regression sweep, manual UAT). Per-ticket review still happens via individual PRs into the milestone branch — Copilot review, lint, tests — so nothing skips the per-ticket gate.

**Promoting a milestone:** once a milestone branch is fully QA'd, open a single PR `epic/<milestone>` → `epic/newsletters-modernisation`. Treat that PR as the integration-test gate.

**Promoting the project:** once the project epic is ready, open a final PR `epic/newsletters-modernisation` → `trunk`. The pre-merge checklist for that step lives in `AGENTS.md`.

**Creating a new milestone integration branch.** When you cut a fresh `epic/<milestone>` from the project epic, also configure repo settings so PRs into it follow the same convention as the project epic:

- **Branch protection:** waive the review-required rule for `epic/<milestone>` (or use a glob pattern like `epic/*` so all integration branches inherit the waiver). Without this, PRs into the new milestone branch are `BLOCKED` by the org-default review-required rule even though Copilot review passes — the per-ticket gate is the Copilot pass at PR time, not a CODEOWNERS approval.
- **CODEOWNERS:** the empty stub on the project epic is inherited automatically when you branch, so no separate action is needed.

Reasoning: long-running integration branches (the project epic and milestone branches alike) intentionally accumulate per-ticket PRs without per-PR human approval. The integration-test gate is the *promotion* PR (milestone → epic, then epic → trunk), not the individual tickets. See the `2026-04-27` Decisions log entry for the original rationale on the project epic.

## Strategy

Replace the MJML rendering pipeline with [`woocommerce/email-editor`](https://packagist.org/packages/woocommerce/email-editor) — an actively maintained PHP package; the same engine MailPoet uses.

**Why:** MJML is a structural problem, not a fixable bug. Every block edit drifts further from email output. WC email-editor produces email-safe HTML from a real Gutenberg post, so the editor and the email finally share a single source of truth. Validated via sandbox spike: posts-inserter, share, and ad blocks all render correctly via ~60 lines of override code.

**Alternatives ruled out:**

- **react-email** — Node/React, doesn't fit the PHP runtime; doesn't solve the block→email mapping problem.
- **Own renderer** — too complex; would duplicate work that's already done in WC email-editor.
- **Patching MJML** — every previous attempt has hit "this is structural, not a bug".

**Override pattern for impedance mismatches.** WC email-editor renderers don't always handle Newspack's block attributes correctly (column percentage-width pixel handling is the first known example). Fixes live downstream:

```php
namespace Newspack\Newsletters\Email_Renderers;

use Automattic\WooCommerce\EmailEditor\Integrations\Core\Renderer\Blocks\Column as WC_Column;

class Column extends WC_Column {
    // Override render_content to fix percentage-width handling.
}
```

**Rollout: dual pipelines behind a feature flag, not a big-bang switch.** Newsletters are brittle and critical — a phased rollout is the safe path. Both pipelines coexist for a soak period:

- New newsletters created with the flag enabled opt into the WC pipeline.
- Existing in-flight newsletters and drafts continue rendering through MJML and must not break.
- A documented migration path lets publishers switch deliberately when ready.
- The flag stays in place until block-by-block QA and email-client testing pass; only then is MJML removed.

**Parallel decision (not solved by replacing the PHP path):** the JS-side `mjml-browser` editor preview in `src/editor/mjml/index.js` also needs to be replaced — either with `@woocommerce/email-editor` JS, a server round-trip, or a hybrid.

## Workstreams

Three workstreams running in parallel:

1. **Editor refactor (MJML → WC email-editor)** — the headline.
2. **Admin UX modernisation** — convert the entire Newsletters admin to React, mirroring `newspack-plugin`'s pattern: DataViews for list surfaces (newsletters CPT, layouts, newsletter ads), React shells elsewhere (settings, layouts authoring), shared scaffolding via `newspack-components`. Layouts becomes a first-class section with its own admin menu and a DataView for management — distinct from the layout-picker / authoring UX nested inside it. Works in both modes: bundled (alongside `newspack-plugin`) and standalone. When `newspack-plugin` is active, its existing Engagement > Newsletters settings page remains canonical; standalone mode is owned by the React settings shell here. Shared components prevent drift between the two settings surfaces.
3. **beehiiv ESP support** — exploring beehiiv as an additional Email Service Provider alongside the existing ones (Mailchimp, ActiveCampaign, Constant Contact).

- **2026-05-05** — **NEWS-1967 — Layouts editor reuses the newsletter editor with send suppressed at three layers; preview-to-email retained.** Layouts now have a dedicated post-editor surface at `post-new.php?post_type=newspack_nl_layo_cpt` (and `post.php?post=…&action=edit`) plus a top-right "Add new layout" primary CTA on the Layouts list. The editor is the newsletter editor minus the campaign-send pipeline. **Publisher-safety property pinned:** publishing a layout *never* dispatches a campaign, regardless of how the post status changes.
  - **Send suppression — defence in depth.** The two callers of `Newspack_Newsletters_Service_Provider::send_newsletter()` (`pre_post_update`, `transition_post_status`) already short-circuit via `Newspack_Newsletters::validate_newsletter_id()`, which strict-matches the newsletter CPT — so layouts have always been excluded from those paths. NEWS-1967 adds a third layer: an early return at the top of `send_newsletter()` itself when `get_post_type( $post ) === NEWSPACK_NEWSLETTERS_LAYOUT_CPT`. The redundancy is deliberate — campaign sends are irreversible, and "future caller bypasses both upstream gates" is the kind of scenario where the cost of a redundant guard is one line and the cost of a regression is a publisher dispatching a layout to their list. Pinned by three PHPUnit cases in `tests/test-layouts-send-suppression.php`: a sanity-check (publishing a newsletter under unconfigured Mailchimp throws a `WPDieException`), an integration assertion (publishing a layout under the same conditions does *not* throw), and a direct assertion (`send_newsletter()` on a layout post returns void without invoking the provider).
  - **Layouts CPT registration delta.** `'public' => false, 'show_ui' => true, 'show_in_menu' => false`. Keeping `public => false` preserves the no-public-URL property; `show_ui` opens `post-new.php` / `post.php` for the CPT; `show_in_menu => false` keeps WP from auto-generating a menu entry that would compete with the React Layouts list. Cap gate (`edit_others_posts`) on registration is unchanged — same posture as NEWS-1929's page capability.
  - **Editor composition — top-level conditional, not scattered guards.** `src/newsletter-editor/index.js` is the entry point. New helper `isLayoutEditor()` in `src/newsletter-editor/utils.js` reads `newspack_email_editor_data.current_post_type`. Module-load gate: `if ( ! isLayoutEditor() ) registerEditorPlugin();` — the `editor/` subplugin is what mounts `<SendButton />` next to WP's publish action via `createPortal`, so skipping its registration is what makes the send affordance physically absent (not hidden via CSS, not no-op'd at runtime). Render-time gate: the `<NewsletterEdit>` JSX branches on `isLayout` to suppress `<PluginPostStatusInfo>` (public toggle), the Newsletter Campaign panel (send-list selector + ESP sidebars), the Layout template-picker panel, and `<ApplyStyling />`. The Testing panel is kept in both modes — that's the preview-to-email path. The init modal also adapts: layouts skip the layout-picker branch (a layout doesn't pick from itself) and only show the API-keys branch when the ESP isn't configured. The styling sidebar title swaps to "Layout Global Styles" when in layout mode.
  - **Editor enqueue — surgical extension, not a rename.** `Newspack_Newsletters_Editor::get_email_editor_cpts()` now lists the layouts CPT alongside newsletters and ads, which makes `is_editing_email()` true and pulls in the shared editor bundle. New `is_editing_layout()` predicate sits alongside `is_editing_newsletter()` — strict semantics preserved on both sides, with the two newsletter-editor enqueue gates (newsletterEditor JS/CSS bundle + conditional-tag support) extended to OR them. `Newspack_Newsletters::branding_scripts` also opts the layouts CPT in so the dark Newspack chrome appears on the layout editor screen for visual consistency.

  - **`has_saved_layouts()` was already removed** — the ticket assumed a conditional menu gate that doesn't exist in trunk. The Layouts list page is registered unconditionally (prebuilts ship in-tree, so the surface is never empty). No change needed.
  - **Empty-state descoped from the original ticket.** The ticket called for an empty state composed via the NEWS-1951 chassis component. Confirmed unreachable in practice — prebuilts always ship — and skipped to keep scope tight. If filters/disablement ever surface a true zero state, DataView's native "no results" treatment is the fallback. The chassis `EmptyState` component remains available for any future need.
  - **"Save as layout" on the newsletter side untouched.** Two entry points to the layouts CPT now coexist: the newsletter editor's "Save as layout" dispatch (existing) and the dedicated layout editor (new). Migration to a single entry point is deferred — the v1 invariant is "both produce the same artefact, the new editor reads either."
  - **Wizard chrome on the layout editor: classic post-editor only.** The layout editor lives at `post.php` / `post-new.php`, not under the admin-shell wrapper, so it gets the standard WP block-editor chrome with no Newsletters wizard breadcrumb. Mirrors how the newsletter editor itself behaves; nothing to override.
- **2026-05-01** — **NEWS-1929 — Layouts list ships with prebuilts merged in, filterable by type; submenu reordering and breadcrumb override land as reusable chassis virtuals.** The Layouts admin surface is a first-class submenu of the Newsletters CPT menu, registered unconditionally — prebuilts ship with the plugin so the surface is never empty, which retired the saved-empty gate that was originally proposed. User-created layouts are born from the editor's "Save as layout" dispatch — *create-from-scratch is out of scope for this PR* and tracked as a high-priority follow-up that adds an "Add new layout" CTA and a layout editor (≈ newsletter editor with send-to-list suppressed but preview-to-email retained). Implementation:

  - **Submenu order via post-hoc reorder, not `add_submenu_page`'s `$position`**: the position arg keys on numeric indices that collide unpredictably with auto-registered CPT submenus and third-party plugins, so passing position 3 doesn't reliably slot between "All Newsletters" (5) and "Add New Newsletter" (10). Layouts returns 2 to slot directly after the auto submenus. Reordering is general-purpose — any future chassis page can declare an index without revisiting WP's submenu mechanics.
  - **Wizard breadcrumb override**: newspack-plugin's wizard renders "Newsletters / All Newsletters" on `edit.php?post_type=…&page=…` URLs because its `admin_screens` map keys on the CPT slug and `get_screen_slug()` prefers the post_type. New chassis virtual `Admin_Page::get_wizard_header_label()` lets a page declare the right text; the existing `patch_wizard_header_active_tab` was generalised to inject a single inline script that handles both tab-highlighting and breadcrumb-patching, with a `MutationObserver` that re-applies on wizard React rerenders. Layouts overrides to `"Newsletters / Layouts"`. Deferred upstream fix in newspack-plugin (the wizard should prefer the page slug over the post_type when both match) is still tracked separately, same posture as the NEWS-1930 wizard-tab workaround.
  - **`mediaField` is grid-only by intent**: the card preview mounts an iframe via `<NewsletterPreview>`/`<BlockPreview>`; in DataView's table layout `mediaField` renders as a leftmost media cell, which inflated each row to ~320px because of the iframe's reserved height. Fix lives at the screen level: `onChangeView` strips `mediaField` when `view.type === 'table'` and restores it when returning to grid.
  - **Lazy-mount per card**: a screen-local `LazyPreview` wrapper uses `IntersectionObserver` to defer mounting until the card scrolls into view; mounted-once-and-stay (re-instantiating an iframe is more expensive than the steady-state memory). Default per-page is 12 (lower than the chassis default of 25) so the in-viewport iframe count stays manageable on first paint.
  - **Block registration on mount**: the admin-shell page isn't a post editor — `parse('<!-- wp:paragraph -->…')` returns `[]` because no blocks are registered. The screen calls `registerCoreBlocks()` (idempotent, guarded against re-registration) on mount. Newspack-specific blocks (posts-inserter, share, ad) intentionally aren't registered here — they live in the much heavier newsletter-editor bundle and pulling that in for the management surface isn't worth the cost; they render as "block-not-found" placeholders in the preview, which is acceptable for a recognition-grade thumbnail.
  - **Inline rename**: title field swaps to a `<TextControl>` when the screen's `renamingId` matches the row id; commits on blur or Enter, reverts on Escape — same ergonomic as `SingleLayoutPreview` in the existing layout picker.
  - **Prebuilts merged in, locked except Duplicate**: the in-tree JSON-seeded layouts (`includes/layouts/*.json`, surfaced via `Newspack_Newsletters_Layouts::get_default_layouts`) are fetched via the existing `/newspack-newsletters/v1/layouts` endpoint, filtered to entries without `post_author`, normalised to the REST shape `useLayoutsData` produces, and pinned at the top of page 1. Synthetic IDs are prefixed `prebuilt-` to avoid colliding with real post IDs; an `is_prebuilt: true` flag drives `isEligible: item => ! item.is_prebuilt` on Edit / Rename / Delete so those actions disappear from the row menu. Duplicate works for both — for prebuilts it skips the `?context=edit` GET and POSTs straight from the in-memory shape, producing a real owned post the user can edit.
  - **Type filter (prebuilt / user-created)**: the `type` field carries `elements` + `filterBy` so DataView surfaces a primary chip; the screen reads `view.filters` to slice the merged data array and adjusts `paginationInfo.totalItems` accordingly (prebuilt-only collapses pagination since the entire prebuilt set fits in one batch).
  - **Pagination respects `view.perPage` even when prebuilts ride along**: page 1 reserves slots for the prebuilt set, so the saved query is **offset-paginated** — page 1 fetches `max(1, perPage − prebuiltCount)` saved rows from offset 0, page 2 starts at that offset and fetches `perPage`, and so on. `paginationInfo.totalPages` is derived from the remainder after page 1's reserved slots. Without this the screen would render `perPage + prebuiltCount` cards on page 1 and silently skip the saved rows that should have appeared above the fold.
  - **REST**: standard `/wp/v2/newspack_nl_layo_cpt` collection for saved layouts (pagination / search / sort / delete / duplicate-via-create / rename-via-PATCH); the legacy `/newspack-newsletters/v1/layouts` endpoint for the prebuilt set, with a new `defaults_only=1` boolean arg that skips the saved-posts WP_Query so the prebuilt fetch doesn't download every saved layout just to filter it out client-side. No new REST class needed.
  - **Wizard `MutationObserver` is scoped and self-disconnects**: the breadcrumb / tab-highlighting patch originally observed `document.body` with `subtree: true` for the lifetime of the page, which is a real cost on React-heavy admin pages. It now observes `.newspack-wizard` (falling back to `body` if the container hasn't rendered yet) and disconnects once both targets are patched, with a `setTimeout(…, 0)` re-arm to defend against the wizard's post-mount rerender.
  - **Inline-rename rejections are swallowed at the field-level commit**: the screen-level handler raises an error notice and leaves `renamingId` set so the inline UI stays available for retry; the field-level `commit()` wraps `await onCommit(…)` in `try/catch` so `onBlur` / `onKeyDown` don't surface unhandled promise rejections in the browser.
- **2026-05-01** — **NEWS-1951 — `rest_pre_insert_<taxonomy>` is unusable for blocking term updates; switched to `rest_request_before_callbacks`.** The natural surface for the parent-self guard on the Advertiser taxonomy looked like `rest_pre_insert_<taxonomy>` (fires from `WP_REST_Terms_Controller::prepare_item_for_database` for both create and update). It is unusable: `update_item` does **not** call `is_wp_error()` on the value `prepare_item_for_database()` returns, so a WP_Error from the filter is cast to an array and silently passed to `wp_update_term`, which then sets `parent=0` and returns 200. `wp_update_term` itself never fires `pre_insert_term` (only `wp_insert_term` does), and `wp_update_term_parent` expects an integer return — no error path. - **2026-04-29** — **Refactored chassis page-highlighting onto `Admin_Page` virtuals.** `Admin_Shell::highlight_parent_menu` and `highlight_submenu` now delegate to per-page `get_parent_file()` / `get_submenu_file()` overrides. Each page owns its own dynamic logic — `Ads_List_Page` chooses the active parent based on `Ads::display_ads_menu_item_separately()` so highlighting tracks the runtime menu placement. Same delegation handles legacy redirects: each page declares its `get_legacy_screen_id()` and `get_legacy_redirect_target()`, and `Admin_Shell::maybe_redirect_legacy_list` iterates pages instead of hard-coding the newsletters CPT.
- **2026-04-29** — **`Ads::rest_api_init` re-namespaced to avoid colliding with the CPT collection route.** The original registration used `register_rest_route( 'wp/v2/' . self::CPT, 'config', … )`, which created a REST *namespace* whose path (`/wp-json/wp/v2/newspack_nl_ads_cpt`) shadowed the CPT's standard collection route — GET requests to the URL returned namespace metadata instead of the post list. Moved the registration to `'newspack-newsletters/v1'` with route `'ads/config'`; updated the only consumer (`src/ads/newsletter-editor/disable-auto-ads.js`). Discovered while wiring NEWS-1930's React DataView, which tries to fetch the same URL.
- **2026-04-29** — **NEWS-1928 — newsletters list replaces the CPT list at the menu-registration level, not via WP_List_Table override.** The auto-generated `edit.php?post_type=newspack_nl_cpt` "All Newsletters" submenu is **kept** as the visible click target; the chassis registers `Newsletters_List_Page` as a **hidden submenu** (`parent=null`) and 302s the legacy URL to the React page via `current_screen`. Why keep the auto submenu rather than replace it: when newspack-plugin's `Newsletters_Wizard` is active, it only recognises URLs that start with `?post_type=newspack_nl_cpt` (its `admin_screens` map). Removing the auto submenu sent WP's first-submenu URL fallback to `admin.php?page=…`, which dropped the Newspack admin-header chrome on top-level menu clicks. `parent_file`/`submenu_file` filters keep the sidebar highlighted on our hidden React page. The list page registers in **both** modes (bundled and standalone) — only Settings remains mode-gated.
- **2026-04-29** — **Status logic lives server-side via a single REST field, not re-derived in JS.** `Newsletters_List_REST::get_status_for_post` returns `{ kind: 'sent' | 'scheduled' | 'draft' | 'trash', sent_at, scheduled_at }` consolidating `post_status`, `Newspack_Newsletters::is_newsletter_sent()`, the WP-scheduled `post_status=future` case, and the `sending_scheduled` meta flag set during ESP dispatch. The DataView's Status column reads `kind` directly. The status **filter**, however, maps to native `post_status` (`publish,private` for "Sent", `future` for "Scheduled", etc.) so server-side filtering stays cheap; the rendering/filter-target mismatch is intentional and visually acceptable.
- **2026-04-29** — **No bulk publish / status-change actions on the list.** The base service-provider class hooks `transition_post_status` to dispatch ESP campaigns — bulk publishing or making private would be irreversible. The DataView exposes only `Edit`, `View public page`, `Make newsletter pages public` / `non-public`, `Trash`, `Restore`, and `Delete permanently`. **Restore** PATCHes `status: 'draft'` for every row; `Newspack_Newsletters_Service_Provider::insert_post_data` then leaves never-sent rows as drafts and forces already-sent rows back to their controlled status (`publish`/`private` per `is_public`). The two `is_public` toggle actions are not purely meta-only: on a `publish`/`private` newsletter they go through `Newspack_Newsletters_Service_Provider::updated_post_meta`, which calls `wp_update_post` and fires `transition_post_status` between `publish` and `private`. They are still safe because the provider's send guard short-circuits when `is_newsletter_sent()` is truthy on already-published rows — so the transition doesn't dispatch a fresh campaign. Status changes that *would* trigger sends (anything reaching `publish`/`private` from a non-sent state) happen exclusively in the post editor where the existing pre-send confirmation guards apply.
- **2026-04-29** — **`@wordpress/dataviews/wp` over `@wordpress/dataviews`.** `/wp` is a self-contained pre-bundled artefact pre-wired for WordPress admin (themed dropdowns, action menus using `@wordpress/components`, unlock-helper for experimental APIs). React is the only peer; no `@wordpress/components`/`@wordpress/i18n` peer alignment to manage. Newspack-story-budget uses the same path.
- **2026-04-29** — **Chassis gains `<PageHeader>` + `useHeaderActions(actions)` hook backed by React context, not a Redux store.** Action shape mirrors `newspack-plugin`'s wizard `setHeaderData({ sectionName, actions })` exactly (`{ type: 'primary' | 'secondary', label, icon?, href?, onClick? }`) so a future consolidation against `newspack-components` is mechanical. Local context keeps the chassis thin — no `@wordpress/data` store registration, no slot fills.
- **2026-04-29** — **Send-list column shows raw IDs in v1.** Resolving `send_list_id` / `send_sublist_id` to friendly names requires a per-provider lookup (`Send_Lists::api_get_send_lists`) that hits the ESP API; a list-fetch round-trip per page render is too expensive without batched/cached resolution. Captured as follow-up work — the list still renders the meta IDs as `<code>` so the column is informative, just not pretty.
- **2026-04-29** — **Milestone integration branches need their own branch-protection waiver.** Discovered when trying to merge PR #2091 into the freshly-created `epic/admin-ux-modernisation`: the merge was `BLOCKED` by the org-default review-required rule because the project epic's review waiver doesn't propagate to new branches. CODEOWNERS does inherit (the empty stub is a file on the branch) but branch-protection rules are repo-config, set per branch or via a glob pattern. Documented the configuration step in *Branch structure* and mirrored the reminder in `AGENTS.md` so future milestone branches are set up at creation time. Recommendation: configure the rule once with a glob like `epic/*` so all integration branches inherit the waiver automatically.

Reasoning: per-ticket gates (Copilot review, lint, tests) still happen at PR time, but the project epic only sees integration-tested units, which is what we need given how brittle the newsletter pipeline is. See *Branch structure* above for the full mechanics.
- **2026-04-29** — **NEWS-1927 chassis: do not displace the existing menu structure.** Initial pass replaced the Newsletters CPT-as-menu with its own top-level menu plus four placeholder submenus, which dropped the auto-generated *All Newsletters* and *Add Newsletter* entries and changed the menu's vertical position. Corrected to keep the CPT's default top-level menu intact (so *All Newsletters*, *Add New*, taxonomies, and the existing Ads submenu all return) and have the chassis register its own pages as **submenus of the CPT menu**. Only the Settings placeholder ships in NEWS-1927 (last in the submenu list, standalone-only); NEWS-1928 to NEWS-1931 each register their own page when they have a real surface to ship. The NEWS-1928 list page took a different approach (`parent=null` + parent_file/submenu_file filters); see the newer entry for that rationale.

## Known gaps / follow-ups

Capabilities the React surfaces don't yet match against WP's classic admin views, captured here so future iterations can decide whether to close them. Not blockers for the current epic, but worth weighing if publisher feedback flags any.

- **Quick Edit / Bulk Edit parity (NEWS-1932).** The classic CPT list lets users update categories, tags, author, status, and other fields inline (per-row Quick Edit, multi-row Bulk Edit). The React DataView ships with bulk *Trash / Restore / Delete permanently / Make public / Make non-public* but no taxonomy/author bulk editing. Real-world usage is unclear — worth measuring before investing in a Bulk Edit modal. If we add it, the obvious shape is a DataView bulk action that opens a modal with a small subset of editable fields, then PATCHes each selected post via REST. Status changes stay off the table for the same reason they're not a per-row action: `transition_post_status` to `publish`/`private` dispatches the ESP campaign.
- **NEWS-1928 list — Send-list column shows raw IDs.** Friendly-name resolution needs a per-provider lookup that hits the ESP API; deferred pending a batched / cached approach (covered in the Decisions log entry for v1).
- **NEWS-1928 list — Public-page filter has no inline counts.** Classic WP shows "Trash (3)" segmented links; the DataView dropdown elides counts. Polish if/when publishers ask.
- **NEWS-1933 — Bulk Edit parity for the ads list (advertiser/placement/category/dates/price).** Shipped without it, mirroring the NEWS-1932 posture for newsletters. Author / status are intentionally out of scope (the ads CPT registration omits `author` support, and the safe bulk status transitions are already covered by Trash / Restore / Delete).
- **NEWS-1952 — Newsletters / Ads empty-state retrofit.** NEWS-1951 introduced the reusable `EmptyState` chassis component and applied it to the Advertisers screen day-one. The Newsletters and Ads list retrofits (using the same component, with their own copy / icon / CTA href) remain on NEWS-1952 as a small follow-up PR. Ad Placement (`newspack_nl_ad_placement`) is **not** a candidate — it's registered with `'show_ui' => false` / `'show_in_menu' => false`, so there is no admin screen for it by design.
