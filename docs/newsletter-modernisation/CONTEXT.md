# Newsletter Modernisation — Context

This document captures the *why* behind decisions for the newsletter modernisation work — rationale, alternatives considered, constraints that shape the work.

## How to use this doc

This is the contract for anyone — human or AI agent — working on this project:

1. **Before starting a session** on any branch in this project (the project epic, a milestone integration branch, or a per-ticket branch off either): read this doc in full. It tells you what's been decided and why, and which open questions still bind.
2. **Before opening a PR**: identify the right base branch (see *Branch structure* below — per-ticket PRs target their milestone branch, not the project epic). Decide whether your work introduces a decision, gotcha, learning, or shift in scope. If yes, update the relevant section and append a dated entry to the **Decisions log** in the same PR. If no context change applies, say so explicitly in the PR description (e.g. "No context change.").
3. **Tone:** terse but explanatory. Future readers won't have the conversation that produced each decision — they need the reasoning, not just the conclusion. Keep entries to load-bearing facts a future agent couldn't recover from code, commits, or tickets.

## Branch structure

Three tiers:

- **`epic/newsletters-modernisation`** — the project epic. Receives only milestone-integration merges. Ultimately merges to `trunk`.
- **`epic/<milestone>`** — one integration branch per Linear milestone (e.g. `epic/admin-ux-modernisation`, `epic/editor-refactor`, `epic/beehiiv`, `epic/de-risk`, `epic/validate`). Receives per-ticket PRs and is QA'd as a coherent unit before promoting to the project epic. Naming: kebab-case version of the Linear milestone name.
- **`news-<id>-<slug>`** — per-ticket branch cut from its milestone integration branch. PRs target the milestone branch.

**Why three tiers.** Newsletters are critical and the modernisation is wide-ranging. We want each milestone to land on the project epic only after it's been tested as a unit (cross-ticket integration, regression sweep, manual UAT). Per-ticket review still happens via individual PRs into the milestone branch — Copilot review, lint, tests — so nothing skips the per-ticket gate.

**Promoting a milestone:** once a milestone branch is fully QA'd, open a single PR `epic/<milestone>` → `epic/newsletters-modernisation`. Treat that PR as the integration-test gate.

**Promoting the project:** once the project epic is ready, open a final PR `epic/newsletters-modernisation` → `trunk`. The pre-merge checklist for that step lives in `AGENTS.md`.

**Creating a new milestone integration branch.** When you cut a fresh `epic/<milestone>` from the project epic, also configure repo settings so PRs into it follow the same convention as the project epic:

- **Branch protection:** waive the review-required rule for `epic/<milestone>` (or use a glob pattern like `epic/*` so all integration branches inherit the waiver). Without this, PRs into the new milestone branch are `BLOCKED` by the org-default review-required rule even though Copilot review passes — the per-ticket gate is the Copilot pass at PR time, not a CODEOWNERS approval.
- **CODEOWNERS:** the empty stub on the project epic is inherited automatically when you branch, so no separate action is needed.

Reasoning: long-running integration branches (the project epic and milestone branches alike) intentionally accumulate per-ticket PRs without per-PR human approval. The integration-test gate is the *promotion* PR (milestone → epic, then epic → trunk), not the individual tickets.

## Strategy

Replace the MJML rendering pipeline with [`woocommerce/email-editor`](https://packagist.org/packages/woocommerce/email-editor) — an actively maintained PHP package; the same engine MailPoet uses.

**Why:** MJML is a structural problem, not a fixable bug. Every block edit drifts further from email output. WC email-editor produces email-safe HTML from a real Gutenberg post, so the editor and the email finally share a single source of truth. Validated via sandbox spike: posts-inserter, share, and ad blocks all render correctly via ~60 lines of override code.

**Alternatives ruled out:**

- **react-email** — Node/React, doesn't fit the PHP runtime; doesn't solve the block→email mapping problem.
- **Own renderer** — too complex; would duplicate work that's already done in WC email-editor.
- **Patching MJML** — every previous attempt has hit "this is structural, not a bug".

**Override pattern for impedance mismatches.** WC email-editor renderers don't always handle Newspack's block attributes correctly (column percentage-width pixel handling is the first known example). Fixes live downstream:

```php
namespace Newspack\Newsletters\Email_Renderers;

use Automattic\WooCommerce\EmailEditor\Integrations\Core\Renderer\Blocks\Column as WC_Column;

class Column extends WC_Column {
    // Override render_content to fix percentage-width handling.
}
```

**Rollout: dual pipelines behind a feature flag, not a big-bang switch.** Newsletters are brittle and critical — a phased rollout is the safe path. Both pipelines coexist for a soak period:

- New newsletters created with the flag enabled opt into the WC pipeline.
- Existing in-flight newsletters and drafts continue rendering through MJML and must not break.
- A documented migration path lets publishers switch deliberately when ready.
- The flag stays in place until block-by-block QA and email-client testing pass; only then is MJML removed.

**Parallel decision (not solved by replacing the PHP path):** the JS-side `mjml-browser` editor preview in `src/editor/mjml/index.js` also needs to be replaced — either with `@woocommerce/email-editor` JS, a server round-trip, or a hybrid.

## Workstreams

Three workstreams running in parallel:

1. **Editor refactor (MJML → WC email-editor)** — the headline.
2. **Admin UX modernisation** — convert the entire Newsletters admin to React, mirroring `newspack-plugin`'s pattern: DataViews for list surfaces (newsletters CPT, layouts, newsletter ads), React shells elsewhere (settings, layouts authoring), shared scaffolding via `newspack-components`. Layouts becomes a first-class section with its own admin menu and a DataView for management — distinct from the layout-picker / authoring UX nested inside it. Works in both modes: bundled (alongside `newspack-plugin`) and standalone. When `newspack-plugin` is active, its existing Engagement > Newsletters settings page remains canonical; standalone mode is owned by the React settings shell here. Shared components prevent drift between the two settings surfaces.
3. **beehiiv ESP support** — exploring beehiiv as an additional Email Service Provider alongside the existing ones (Mailchimp, ActiveCampaign, Constant Contact).

## Decisions log

Decisions still binding on future work. Newest first.

- **2026-05-11 — NEWS-2198 — Admin-shell pages don't enqueue `wp-block-editor`, so BlockPreview-using surfaces must inline the rules they need** — `transform-origin: top left` on `.block-editor-block-preview__content` plus the two `.block-editor-iframe__*` height/width rules, scoped to the local wrapper. Enqueuing the full sheet rejected (~250KB, cascades onto unrelated admin-shell surfaces). **Hairline borders that overlap absolute-positioned children should use `border` + `border-radius`, not `box-shadow: inset`** — inset shadows paint in the background layer and get covered by content. **Iframe lifecycle on Grid → Table is clean** (WeakRefs detach + GC within ~100ms); the "9 iframes persist" observation in the original scope was a measurement artefact, not a leak.
- **2026-05-11 — NEWS-2199 — Admin-shell notices must go through `notifySuccess` / `notifyError` (`src/admin-shell/notices.js`).** `<ShellNotices>` in `app.js` only renders entries with `type === 'snackbar'`; bare `createSuccessNotice` / `createErrorNotice` calls land in `core/notices` but never reach the user. Helper pre-binds the snackbar flag and defaults errors to `explicitDismiss: true` so the `aria-live` announcement isn't auto-dismissed before screen-reader users can read it.
- **2026-05-11 — NEWS-2200 — `newspack-components`'s `dist/esm/wizard/index.js` re-registers `newspack/wizards` on every barrel import.** Worked around with `NormalModuleReplacementPlugin` stubbing the wizard module (`webpack-shims/newspack-components-wizard.js`). **Fragility:** the regex matches an internal build artefact, not a stable public path — a major bump that reorganises `dist/` would silently bypass the replacement and re-introduce the warning. Durable upstream fix: idempotent `registerStore()` in `newspack-components` (guard on `wp.data.select(name) === undefined`) — separate cross-repo concern. **Subpath imports rejected first:** existing `__mocks__/newspack-components.js` Proxy intercepts only the bare specifier, subpaths hit raw ESM jest can't parse, and newspack-scripts hardcodes `--config` so a project-level `moduleNameMapper` is replaced wholesale, not merged.
- **2026-05-11 — NEWS-2197 — Filter-dropdown population uses one consolidated `/newspack-newsletters/v1/newsletters-list/filter-options` endpoint, not three standard WP REST collections.** Three reasons that bind future filter additions: (i) `/wp/v2/users` is gated by `list_users` (admin-only), which would leave editors with an empty Author dropdown; (ii) `/wp/v2/users` / `categories` / `tags` cap at `per_page=100`, silently truncating on large sites; (iii) usage-scoped options (each list scoped server-side to authors / terms / send-list IDs *actually used on newsletters*) keep the dropdown honest. Permission gate mirrors `edit_posts` on the newsletters CPT. Send-list narrowing translates `newspack_newsletters_send_list_id` into a custom `meta_query IN` because there's no native `?meta_value=` collection param.
- **2026-05-11 — NEWS-2196 — Ads list meta-based sorts: virtual orderby tokens at the URL, LEFT-JOIN `posts_clauses` filter underneath.** The WP REST orderby enum doesn't accept `meta_value` / `meta_value_num`, and `rest_validate_request_arg` rejects ahead of any `rest_${CPT}_query` filter — so meta-backed sort URLs 400'd before translation could land. Surface uses virtual tokens (`?orderby=price`) translated server-side; `VIRTUAL_ORDERBY_TOKENS` is a single class constant so adding a sortable column is one place. **Sort mechanism:** permanent stateless `posts_clauses` filter with a LEFT JOIN, not WP_Query's `meta_key + orderby=meta_value*` pass-through. The pass-through INNER JOINs `postmeta` and silently drops rows missing the key — fresh ads with no `start_date`/`price` and ads with no tracking activity (no persisted impressions/clicks row) would vanish on column-header click. `$args['orderby'] = 'none'` so WP's default ORDER BY drops out. Numeric sort uses `meta_value + 0`, not `CAST AS SIGNED` — the editor's `step=0.01` price field would otherwise collapse 10.01 vs 10.99 both to 10.
- **2026-05-08 — NEWS-2037 — Bundled-mode QA pass: five follow-ups filed, each with its own decision-log entry.** NEWS-2196 (blocker — ads meta sorts), NEWS-2197 (filter parity), NEWS-2198 (layouts iframe lifecycle), NEWS-2199 (silent notices), NEWS-2200 (wizards registration). Layouts editor send-suppression confirmed live: `/v1/layouts/<id>/test` returns 409 ("save first") on missing rendered HTML, per-provider `/test` returns 404 for layouts. Trunk-vs-companion smoke passed — the wizard-bridge bundle is inert when newspack-plugin's wizard hasn't been updated, no regression on plain trunk before #4707 lands.
- **2026-05-07 — NEWS-2175 — `auto-draft` rows count as draft in the admin lists.** Visiting `post-new.php` writes an `auto-draft` row immediately; without this, opening the editor would invisibly grow the drafts count.
- **2026-05-07 — NEWS-2168 — ESP-row edit lifted into the shared modal; bulk Save button retired in favour of per-row commits.** Per-row immediate persistence matches the modal Save / toggle flip pattern across the shell — a global Save button felt disconnected from the per-row UI.
- **2026-05-07 — NEWS-2152 — Bundled-mode parity for the local-list modal via event-driven mount handoff, not a full Subscription Lists port.** Wizard-bridge ships a window-scoped `EVENTS` contract; newspack-plugin's wizard listens and our modal mounts under bundled mode's chrome. Readiness flag is durable so late subscribers don't miss the signal. Lets us land the modal here while newspack-plugin's full Subscription Lists port happens separately.
- **2026-05-06 — NEWS-2093 — Local list create/edit goes through `LocalListModal`, not the classic CPT editor.** Visibility uses `Newspack_Newsletters_Subscription::get_filtered( is_local )`, **not** `get_configured_for_current_provider` — without this fix a freshly-created list (no ESP audience picked yet) was invisible until the user opened the legacy editor. Rejected flipping the CPT's `show_in_rest => true`: opens up `/wp/v2/newspack_nl_list` GET/PATCH/DELETE that nothing currently exposes, switches the inline Edit link to block editor (the existing classic ESP-wiring form would break), and `Subscription_Lists::save_post` is nonce-gated to the classic form so a `wp/v2` POST also creates a bare list — same end state as the custom route.

- **2026-05-06 — NEWS-1952 — Empty-state pattern for list surfaces.** Strict-empty only (unfiltered list returns zero after first fetch); filter / search empty-results keep DataView's native treatment. **Two-flag gate:** `hasResolved` flips after the first fetch attempt (success or failure) — drives the spinner so a first-load error renders the DataView (where the error notice surfaces failure) rather than sticking on the placeholder; `hasLoadedOnce` flips only on a successful response — drives the strict-empty check so a transient failure can't trigger the onboarding banner. Same gate suppresses `useHeaderActions` registration: bundled-mode wizard's action portal lives outside `.newspack-newsletters-admin` and CSS `:has()` can't reach it, so the only reliable suppression is to never register the action until the list has rows. **Trash-only lists fall through to the DataView:** each hook fires a one-shot `?status=trash&per_page=1` probe; `trashCount` starts `null`, set on success, stays `null` on failure — `isStrictEmpty` requires `trashCount === 0` (false when null). Advertisers don't have trash. **Don't clobber `data` / `paginationInfo` on fetch failure** — preserves last-good so a refetch error doesn't flash the onboarding banner. **`newspack-icons` ships raw JSX:** webpack rule `exclude: /node_modules[\\/](?!newspack-icons[\\/])/` + `__mocks__/newspack-icons.js` Proxy stub so jest can resolve transitive imports.
- **2026-05-05 — NEWS-1967 — Layouts reuse the newsletter editor with the entire ESP-campaign pipeline suppressed.** Publisher-safety property pinned: a layout *never* dispatches a campaign and *never* creates or updates an ESP campaign object, regardless of post status or save path. **Send suppression is defence-in-depth:** the existing `Newspack_Newsletters::validate_newsletter_id()` strict-matches the newsletter CPT (already excludes layouts), plus a new early return at the top of `send_newsletter()` when post_type is the layout CPT. Redundant by design — campaign sends are irreversible. Pinned by `tests/test-layouts-send-suppression.php`. **Sync suppression on save:** each provider's `save()` callback (hooked on `updated_post_meta`) early-returns when post_type is the layout CPT — without this, saving a layout would create or update an ESP campaign object. **Editor composition gates on `isLayoutEditor()`** (reads `<body>`'s `post-type-{cpt}` class — available on every post editor screen). Module-load gate skips `registerEditorPlugin()` so `<SendButton />` is physically absent (not hidden, not no-op'd). Render-time gate suppresses the public toggle, Newsletter Campaign panel, and Layout template-picker panel; `<ApplyStyling />` is kept (live preview side effects). **Preview-to-email uses a layout-specific route** (`POST /v1/layouts/{id}/test`) that wraps `EMAIL_HTML_META` and dispatches via `wp_mail()` — no ESP campaign created. Reuse of the per-provider `/test` route was rejected: it's gated by the strict newsletter validator and internally calls `sync()` to ensure an ESP campaign exists.

Self-contained shell uses `newspack-components` primitives. UI drift is the known accepted trade-off. **Legacy banner gated to bundled mode:** `Newspack_Newsletters::branding_scripts` (navy "N" + white strip) was enqueued on every Newsletters CPT screen; in standalone there's no surrounding wizard chrome for it to anchor to, so it overshoots WP's gutter as a logo + empty strip. Skip when `! - **2026-05-01 — NEWS-1929 — Layouts list reusable chassis virtuals.** Two patterns that bind future chassis pages. **Submenu order via post-hoc reorder, not `add_submenu_page`'s `$position` arg:** position arg keys on numeric indices that collide unpredictably with auto-registered CPT submenus and third-party plugins. New `Admin_Page::get_submenu_index()` returns a 0-based index; `Admin_Shell::reorder_submenus` runs on `admin_menu` priority 999 (after every contributor) and splices entries into place. **Wizard breadcrumb override** via `Admin_Page::get_wizard_header_label()`: newspack-plugin's wizard renders "Newsletters / All Newsletters" on `edit.php?post_type=…&page=…` URLs because its `admin_screens` map keys on the CPT slug. Page 1 reserves slots for prebuilts so the saved query offset-paginates. **Block registration on mount:** the admin-shell page isn't a post editor — `parse()` returns `[]` without `registerCoreBlocks()`. Newspack blocks deliberately not registered (live in the heavier newsletter-editor bundle, render as "block-not-found" placeholders, acceptable for recognition-grade thumbnails).
- **2026-05-01 — NEWS-1951 — `rest_pre_insert_<taxonomy>` is unusable for blocking term updates; switched to `rest_request_before_callbacks`.** `WP_REST_Terms_Controller::update_item` doesn't call `is_wp_error()` on the value `prepare_item_for_database()` returns, so a WP_Error from the filter is cast to an array and silently passed to `wp_update_term`, which then sets `parent=0` and returns 200. `wp_update_term` itself never fires `pre_insert_term` (only `wp_insert_term` does). Worth re-checking if a future WP release adds the missing `is_wp_error` check on the prepared term.
- **2026-04-30 — Ads lifecycle accepts WP `future` post status alongside meta-driven scheduling.** Two ways to define `kind=scheduled`: `publish`/`private` row with `start_date` meta in the future (existing path), or `post_status=future` (WP's standard scheduler). Without the `future` branch, ads scheduled through the normal WP scheduler would silently disappear from the React list. On a `future` row, `start_date` / `expiry_date` meta are ignored — WP's scheduling owns the lifecycle until the row publishes. (`active` and `expired` buckets stay publish/private only — those rows haven't published yet.)
- **2026-04-29 — Hidden React pages must register under two hooknames.** `add_submenu_page(parent, …)` registers the callback under the hookname WP computes from `parent`. That matches `user_can_access_admin_page()`'s lookup but **not** `admin.php` line ~182's URL-derived lookup (`$pagenow . '?post_type=' . $typenow`). When `typenow` isn't itself a top-level menu (true for the ads CPT in submenu mode), the URL-derived hookname falls back to the `admin_page_*` prefix and the page 500s with "Cannot load X". `Admin_Shell::register_menu` mirrors hidden pages under `admin_page_<slug>` after the standard `add_submenu_page` call.
- **2026-04-29 — NEWS-1928 — Newsletters list replaces the CPT list at the menu-registration level, not via `WP_List_Table` override.** Auto-generated `edit.php?post_type=newspack_nl_cpt` "All Newsletters" submenu is **kept** as the click target; chassis registers a hidden submenu (`parent=null`) and 302s the legacy URL to the React page via `current_screen`. Why keep the auto submenu: newspack-plugin's `Newsletters_Wizard` only recognises URLs starting with `?post_type=newspack_nl_cpt`. Removing the auto submenu sent WP's first-submenu URL fallback to `admin.php?page=…`, which dropped the Newspack admin-header chrome on top-level menu clicks.
- **2026-04-29 — Status logic lives server-side via a single REST field, not re-derived in JS.** `Newsletters_List_REST::get_status_for_post` returns `{ kind, sent_at, scheduled_at }` consolidating `post_status`, `Newspack_Newsletters::is_newsletter_sent()`, `post_status=future`, and the `sending_scheduled` meta flag. The status **filter** maps to native `post_status` (`publish,private` for "Sent", `future` for "Scheduled", etc.) so server-side filtering stays cheap — the rendering/filter-target mismatch is intentional.
- **2026-04-29 — No bulk publish / status-change actions on newsletter or ads lists.** Service-provider base class hooks `transition_post_status` to dispatch ESP campaigns — bulk publishing or making private would be irreversible. The list exposes only Trash / Restore / Delete permanently / Make public / Make non-public. Restore PATCHes `status: 'draft'` for every row; `insert_post_data` then leaves never-sent rows as drafts and forces already-sent rows back to their controlled status. The `is_public` toggle is not purely meta-only — on `publish`/`private` rows it fires `transition_post_status`, but the provider's send guard short-circuits when `is_newsletter_sent()` is truthy, so it doesn't dispatch a fresh campaign.
- **2026-04-29 — `@wordpress/dataviews/wp`, not `@wordpress/dataviews`.** `/wp` is pre-bundled for WordPress admin: themed dropdowns, action menus using `@wordpress/components`, unlock-helper for experimental APIs. React is the only peer.
- **2026-04-29 — Milestone integration branches need their own branch-protection waiver.** Discovered on PR #2091 into a fresh `epic/admin-ux-modernisation`: the org-default review-required rule BLOCKED the merge even though Copilot review passed, because the project epic's review waiver doesn't propagate to new branches. Configure once with a glob like `epic/*` so all integration branches inherit. See *Branch structure* and the pre-merge checklist in `AGENTS.md`.
- **2026-04-29 — NEWS-1927 chassis is a thin scaffold, not a port of newspack-plugin's `Wizard`.** Closer to `newspack-popups`' settings: a single React mount per `?page=` slug, no `HashRouter` at the chassis level. Each screen does its own internal routing if it needs to. Chassis does **not** displace the existing CPT menu: it registers as submenus of the CPT menu so *All Newsletters*, *Add New*, taxonomies, and the existing Ads submenu all remain.
- **2026-04-27/28 — Epic-only `AGENTS.md` addendum + `.github/CODEOWNERS` stub.** Both are scaffolding for long-running iteration on the project epic. The "Working on `epic/newsletters-modernisation`" section in `AGENTS.md` points agents at this doc as the binding contract for sessions on the epic and any milestone integration branch. ## Known gaps / follow-ups

Capabilities the React surfaces don't yet match against WP's classic admin views, captured here so future iterations can decide whether to close them. Not blockers for the current epic, but worth weighing if publisher feedback flags any.

- **Quick Edit / Bulk Edit parity (NEWS-1932).** The classic CPT list lets users update categories, tags, author, status, and other fields inline (per-row Quick Edit, multi-row Bulk Edit). The React DataView ships with bulk *Trash / Restore / Delete permanently / Make public / Make non-public* but no taxonomy/author bulk editing. Real-world usage is unclear — worth measuring before investing in a Bulk Edit modal. Status changes stay off the table for the same reason they're not a per-row action: `transition_post_status` to `publish`/`private` dispatches the ESP campaign.
- **NEWS-1928 list — Send-list column shows raw IDs.** Friendly-name resolution needs a per-provider lookup that hits the ESP API; deferred pending a batched / cached approach.
- **NEWS-1928 list — Public-page filter has no inline counts.** Classic WP shows "Trash (3)" segmented links; the DataView dropdown elides counts. Polish if/when publishers ask.
- **NEWS-1933 — Bulk Edit parity for the ads list (advertiser/placement/category/dates/price).** Shipped without it, mirroring the NEWS-1932 posture for newsletters. Author / status are intentionally out of scope.
- **NEWS-2037 cosmetic / low-priority gaps.** Surfaced during the bundled-mode QA pass; not blocking ship.
  - Author column blank for newsletters with `post_author = 0`. Render "(no author)" or "Unknown" instead of an empty cell.
  - Ads list Categories column has no filter. The server supports `?categories=` natively via the standard WP REST controller; just not surfaced in the field def.
  - Advertisers `PATCH /wp/v2/newspack_nl_advertiser/<id>` with `parent=<descendant_id>` returns 200 but WP's `wp_update_term_parent` cycle detection silently demotes the term to top-level. UI prevents this case (TreeSelect filters out descendants), but a third-party REST caller would see a successful response and an unexpected demotion. Mirror the parent-self `rest_request_before_callbacks` guard for descendants too.
- **NEWS-1952 — Newsletters / Ads empty-state retrofit.** NEWS-1951 introduced the reusable `EmptyState` chassis component and applied it to the Advertisers screen day-one. Newsletters and Ads list retrofits remain on NEWS-1952 as a small follow-up PR. Ad Placement (`newspack_nl_ad_placement`) is **not** a candidate — it's registered with `'show_ui' => false` / `'show_in_menu' => false`, so there is no admin screen for it by design.
